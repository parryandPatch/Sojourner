## Acceptance criterion check

The spec requires the initial plan and a revised plan to appear in under 8 seconds on a normal laptop. Each figure below is the wall clock for the **whole** three-option solve — option enumeration, the solve itself, auditing, and metrics — which is the number a user actually waits for.

- Initial frontier: min 840 ms, median 842 ms, max 844 ms → **met** against the 8000 ms criterion.
- Revised solves (24 event × clock combinations): fastest 28 ms (`Revised solve — EVENT_A @ min 120`), slowest 131 ms (`Revised solve — EVENT_B @ min 180`) → **met** against the 8000 ms criterion.
- The planner's own `solve_time_ms` field is CP-SAT's accounting and excludes option enumeration, auditing, and metric computation. Every figure above is wall clock and includes all of that.
- These timings exclude HTTP, database, and rendering. The end-to-end time a user perceives is longer and was not measured here.

## Option distinctness observed during this run

The spec asks the planner to "return exactly three distinct options" and sets the acceptance criterion "three trade-off plans are visibly different on the seeded scenario". The two are not the same claim, and the difference shows up here. The initial solve, where all 13 missions are free to be decided, produces three distinct options. A re-plan re-opens only the missions the event affected — the spec's own re-planning rule — and when that leaves one or two decisions, all three objectives genuinely select the same option and only one plan exists. Note also that a free mission with only one feasible asset is not a real decision at all, however many missions are open.

- 7 of 24 re-plans produced three distinct options; 17 produced fewer.
- Grouped by how many missions the re-plan was free to decide. This is a correlation, not a law — see the reading below:

| free missions | re-plans | three distinct options |
| ---: | ---: | ---: |
| 1 | 1 | 0 |
| 2 | 3 | 0 |
| 3 | 7 | 0 |
| 4 | 1 | 1 |
| 5 | 5 | 3 |
| 6 | 4 | 2 |
| 7 | 2 | 1 |
| 8 | 1 | 0 |

  Reading the table: free-set size raises the odds but does not settle them. Every case with one free mission failed to produce three options — with a single decision there is nothing for three objectives to disagree about, and no choice of weights can manufacture a third answer because none exists. Above that, the outcome depends on whether the free missions actually have competing options: a large free set whose missions each have one feasible asset will also collapse, since re-deciding them was never a real choice.
- The planner reports this rather than perturbing a plan until it looks different: the API returns `duplicate_options` and `distinct_options_note`, and the UI marks the identical cards. Manufacturing a third answer would put a label on a plan embodying an objective the solver never optimised.

Note the `variants=1` above. The greedy fallback does not consult the variant weights — it walks the option pool in a fixed order and takes the first feasible choice for each mission — so when it triggers, all three options converge on the same plan. That is reported rather than hidden: the API returns `duplicate_options` and `distinct_options_note`, and the UI marks the identical cards, so nobody is shown a fabricated trade-off. A Commander who sees three identical cards knows the solver did not answer, which is the honest reading of a run that hit its budget.


### Can different objective weights do better?

An earlier draft of this report asserted that the count above was independent of the objective weights. That assertion was wrong, and this table is the correction: each weighting below was run over the same 24 disrupted states, with the same parent plans, changing only the weights. The count moves, by more than expected.

| weighting (coverage / safety / stability) | 3 distinct | 1 distinct | keeps the spec's objective |
| --- | ---: | ---: | :---: |
| current (6/3/8, 900/0/0, 6/1/40) | 7/24 | 0/24 | yes |
| control — all three variants identical | 0/24 | 24/24 | n/a (control) |
| control — drop_cost from coverage (objective reduced) | 5/24 | 1/24 | n/a (control) |
| control — drop risk from coverage (constraint removed) | 6/24 | 0/24 | n/a (control) |
| alt A — coverage dominant (300/300/300, 900/1/1, 1/1/1) | 10/24 | 0/24 | yes |
| alt B — risk-only spread, cost kept (6/1/0, 2000/0/0, 6/0/120) | 13/24 | 0/24 | yes |
| alt C — extremes (1/1/1, 4000/0/0, 1/1/4000) | 8/24 | 0/24 | yes |
| alt D — safety dominant (1/1/1, 500/0/0, 1/1/1200) | 8/24 | 0/24 | yes |
| alt E — low safety risk weight (6/3/8, 40/0/0, 6/1/40) | 7/24 | 0/24 | yes |
| alt F — change-averse everywhere (6/3/3000, 900/0/3000, 6/1/6000) | 0/24 | 8/24 | yes |
| alt G — equal spread (10/10/10, 1000/10/10, 10/10/200) | 7/24 | 2/24 | yes |

The first control — all three variants given identical weights — scored 0/24 three-distinct and 24/24 collapsed to one. That is the expected result and confirms the measurement is reading distinctness rather than something correlated with it.

The shipping weighting reaches 7/24. The best alternative that *keeps* the specified objective reaches 13/24 (`alt B — risk-only spread, cost kept (6/1/0, 2000/0/0, 6/0/120)`), so tuning within what the spec allows moves the number by +6.

**Where the extra options came from.** Comparing the shipping weighting against `alt B — risk-only spread, cost kept (6/1/0, 2000/0/0, 6/0/120)` problem by problem, it rescues 8 of 24 re-plans that had collapsed. The free-set sizes of the rescued cases: 2, 2, 3, 3, 3, 3, 5, 8.

Some rescued cases had only 2 free mission(s). So the shipping weighting collapses more often than it strictly has to, and the clean version of the argument — *no weighting can help, because with one or two decisions there is only one answer* — is wrong at the low end. What survives is narrower: the collapse rate is strongly driven by how many decisions are open (see the table above), and a free mission with one feasible asset is still not a real decision at any weighting.

That leaves a decision this report should not pretend is settled. The 8 extra distinct options are real — they are different plans, each auditor-valid, each honouring the coverage floor — so adopting this weighting would not be fabrication; it would be a better-tuned planner. It was not adopted, because the weights were chosen on their merits before this measurement existed, and re-picking them to maximise a distinctness count found afterwards is precisely the scoreboard-chasing this project is supposed to avoid. A reviewer who prefers `alt B — risk-only spread, cost kept (6/1/0, 2000/0/0, 6/0/120)` has a defensible case and a reproducible table above.

One caution on reading this table as licence to re-pick the weights by score. The count is a proxy for a real property — how often a Commander is shown three genuine alternatives — and it is not the only one. Coverage achieved, mean risk, and cost are the reasons the weights were set the way they were, and this sweep measures none of them. A weighting that scores higher on distinctness while delivering worse plans would be a worse planner with a better-looking report, and this table cannot tell the difference. Evaluating that properly means auditing the plan quality of each alternative, which has not been done.

The shipping weighting is kept and the collapse it produces is reported. That is a defensible position, not a proven one.

## What this does not tell you

- Nothing about HTTP latency, database throughput, concurrent users, or frontend render time. None of those were measured.
- Nothing about real operations. The scenario is synthetic and small by construction; a real planning problem would have orders of magnitude more entities.
- The timings are from one machine on one day. Re-run the script after a change rather than comparing against these numbers across machines.
